# 1. Ведём логи архитектурных решений

**Date**: 2026-09-22

**Status**: Accepted

## Context

Проект накапливает архитектурные решения (выбор UI, структура слоёв, транспорт RPC,
модель провайдеров), но они размазаны по спекам, справочникам и памяти участников.
Без фиксации «почему» новые изменения рискуют сломать принятые компромиссы.

## Decision

Ведём Architecture Decision Records (ADR) в `Plan/adr/`, по формату Michael Nygard
(Status / Context / Decision / Consequences), по одному файлу на значимое решение.

## Consequences

- Решения и их обоснования перестают теряться; новичок (или агент) видит историю.
- Появляется точка сверки для ревью: меняешь решение — пиши новый ADR и помечай
  старый `Superseded`.
- Небольшой накладной расход: содержательный ADR пишется осознанно.
